- Подпись управляется закрытым ключом **владельца** и двумя секретами GitHub.

### Что владельцу нужно сделать ОДИН РАЗ

1. Сохраните в двух независимых безопасных местах файл `NEON_CASINO_ANDROID_RELEASE_KEY_KEEP_PRIVATE.p12` и пароль от него. Если потерять ключ при самостоятельном распространении APK, обычные обновления с прежней подписью будут невозможны. Не публикуйте `.p12` и пароль в Issues, репозитории, PR, чатах с третьими лицами.
2. GitHub → репозиторий → **Settings → Secrets and variables → Actions → New repository secret**.
3. Создайте секрет `NEON_RELEASE_KEYSTORE_B64` со **всем содержимым** приватного текстового файла `GITHUB_SECRET_NEON_RELEASE_KEYSTORE_B64_KEEP_PRIVATE.txt` (это base64 от P12, не имя файла).
4. Создайте секрет `NEON_RELEASE_PASSWORD` со всем содержимым `NEON_CASINO_ANDROID_RELEASE_PASSWORD_KEEP_PRIVATE.txt`, без конечного перевода строки.
5. Напишите «секреты настроены». Выпуск запускается **только** изменением файла `.ci/release-request.txt` в ветке `qa/release-signing-20261104`. Workflow называется `NEON Android owner-key signed release`. Он **не** выполняется от обычных коммитов. Пока двух секретов нет, подписывать ничего нельзя.

### Как удостовериться, что релиз подписан правильно

GitHub workflow выполняет:
- `gradle :app:assembleRelease` — release APK, НЕ Debug/QA;
- `apksigner verify --verbose --print-certs` — v2-подпись и сертификат;
- `aapt dump badging` — пакет и versionCode, приложение **не debuggable**;
- сверку отпечатка с указанным SHA‑256; при расхождении публикация блокируется.

**Обязательно:** это новый ключ. Прежние APK могли использовать другой пакет или другой сертификат. В таком случае Android не разрешит обновить их поверх старой установки. Перед распространением сравните сертификат установленного приложения и нового APK. Нельзя обещать отсутствие потери данных без такой проверки. Для старой установки используйте экспорт JSON при наличии и проверьте импорт в новой версии на резервной копии.

### RuStore и Google Play

При публикации через сторонние магазины проверьте правила передачи и владения подписью; не путайте ключ подписи APK с upload key для Google Play App Signing. При Google Play App Signing Google подписывает конечный APK собственным app-signing key; загрузочный сертификат может быть другим.

## iPhone/iPad: настоящее Apple-подписание

Apple-сертификат **невозможно выпустить от имени пользователя** без его Apple Developer Team. Нужны собственная Apple Developer учётная запись/Team, идентификатор приложения, профиль provisioning и подпись в Xcode.

В исправленном проекте NEON используется bundle ID `com.neon.royale.ios` и версия `1.8.9 (190)`. На Mac:
1. Откройте `NEONROYALE.xcodeproj` в Xcode.
2. Target → Signing & Capabilities → отметьте **Automatically manage signing**, выберите принадлежащую вам Team.
3. Выберите физический iPhone для тестов и запустите приложение, либо Product → Archive → Distribute App для подписанной IPA (доступный метод зависит от членства и профилей).
4. Сверьте Bundle Identifier с существующей установкой и выполните резервное копирование перед миграцией.

Для распространения Mac .app вне App Store требуется Developer ID и обычно нотариализация Apple; для доверенной подписи Windows EXE требуется собственный доверенный сертификат издателя. Таких учётных данных в проекте нет, эти подписи не созданы.
